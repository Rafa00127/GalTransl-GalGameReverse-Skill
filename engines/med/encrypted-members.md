# MED / 加密成员与 artemina 方言

`MDE0` 是 **已实现** 的容器 profile（`mde0-additive-member-v1`）：[归档层](../../python/archives/med.py) 负责解密/重加密，[工作流](../med.md) 通过 `--key` 接收显式密钥。本页记录算法、相位、密钥反推方法以及仍需实测的边界，避免再次踩到"能自反却解错"的坑。

## 容器与成员分层

- magic 决定成员存放方式：`MDN0` 明文，`MDE0` 加法成员编码。两者共用 16 字节头（偏移 4 u16 索引项宽度、偏移 6 u16 成员数、8–15 保留）与从 `0x10` 起的索引。
- 索引项末尾 8 字节固定是 `u32 长度`、`u32 绝对偏移`；宽度 26 的条目在长度前还有一个来源不明的 u32（`name[14] + u32 + 长度 + 偏移`）。它不是长度也不是偏移，读名字槽（`width-8`）仍然安全，但 writer 必须原样保留这 4 字节。
- 容器索引明文不意味着成员明文，也不代表所有 `MDE0` 成员都用同一密钥或同一算法。未知 magic、未知成员分布应补独立 profile，不放宽现有 parser。
- 名称 CP932/NUL 槽中 NUL 之后的残留字节、保留字段及成员间隙都要保持。

## 加法成员编码与相位

使用调用方给出的非空字节 key（工具侧常以 ASCII 关键字或十六进制传入）。成员前 `0..0x0F` 保持不动；对成员内偏移 `p ≥ 0x10`：

```text
解密：plain[p] = (coded[p] + key[(p - 0x10) % len(key)]) & 0xFF
加密：coded[p] = (plain[p] - key[(p - 0x10) % len(key)]) & 0xFF
```

两个细节都属于实测结论：

1. **相位从第一个编码字节起算**（`p - 0x10`），不是从成员起点 `p % len(key)`。两者只在 `0x10` 处重合，之后每次错开；按 `p % len` 解仍会得到大段"像日文"的字节，但头字段、帧长度和字符串池会对不上。
2. `p` 是**成员内偏移**，不是文件绝对偏移；索引与归档尾部不参与变换，也不给整个归档施加该变换。

## 已知明文反推密钥

若某成员里已可靠确认存在固定结构（例如 `\x00#RULE_...` 这类标记字面量），对候选周期 `K`：

```text
对已确认明文的第 j 个编码区字节（j 从 0 起，对应成员偏移 0x10 + j）：
key[j % K] = (plain[0x10 + j] - coded[0x10 + j]) & 0xFF
```

要求：

- 同一周期位置在多个独立字段/成员上必须一致；
- 候选密钥必须让**整个**成员结构自洽：`LE32[0]+16 == 成员长度`、代码区长度、两个 u16 池计数、标签表、字符串池 NUL 结尾、引用序号全部落在池内；
- 短重复前缀可能对应多个周期，不能选第一个"看起来像日文"的结果。

**一个反例值的代价**：已知明文中把 `RULE` 误写为形状相近的 `RUNE`，只会让一个密钥字节错（`M` 写成 `K`）。这个错误密钥仍能自反往返、也仍能解出大部分可读日文，症状却是每 24 字节错一字节——正文个别字变成相邻字，脚本末尾的零哨兵被解成非零，导致脚本名表损坏、开场被跳过。**"能解出可读文本"不是密钥正确的证据**，必须逐层核对结构字段。密钥与样本本身不随包内置。

## 脚本语义兼容条件

明文线索为：总长减 16、代码长度、两个 u16 池计数、代码相对 u16 标签表、主字符串池和标签名池；帧是 `u16 source_line + u8 hint + u8 opcode + 参数`，整帧长 hint+3。末端零哨兵、参数形状及引用角色须匹配现有 profile 后才能交给 writer，hint 能划帧不代表未知 opcode 已有语义。

仅按 opcode 或日文外观导出所有池项会混入资源、规则表、导航菜单和标题。姓名是否持续、清名指令、正文显示调用与选择目标应按当前 VM 核对；备忘录的"姓名只影响下一句""首次译名优先"不能覆盖现有 MED profile 已验证规则。共享池项可能同时是对白和资源名，应按引用隔离变化，而不是改整个原槽。

验证顺序：明文 parser/writer 往返 → 变长重解析 → 加减法及正确相位向量 → 密钥候选反例（错误密钥必须被结构校验拒绝）→ 重新编码后整体解包/解析 → 未改成员逐字节一致。索引能列出或变换能自反，都不能证明密钥与文本语义正确；没有游戏内显示验证时仍明确"未验证显示"。

## 第三方工具的接线方式（仅作方言证据）

翻译肋手 v4.9D 的 `GameRes.DxLib.ArcMED` 提供了一条可核对的行为线索：

- 容器层只检查前两字节 `MD`；打包时普通包写 `MDN0`，文件名（去扩展名）以 `_scr` 结尾时写 `MDE0`。
- `_scr` 同时是成员解密的开关：只有该命名约定才从成员内偏移 16 起做加法，其他包按明文处理。
- 密钥来自调用方输入的十六进制文本，工具不内置任何密钥，也不尝试推断。
- 该工具文档写 `key[p % len(key)]`（`p` 为成员内偏移）；**按本页实测相位 `(p - 0x10)` 才对**，上面的错误排布即由此而来。
- 打包路径按目录名而非实际内容决定是否加密，回填后必须在真实成员上重新确认相位。

这些是**单一工具的接线选择**，不是 MED 通性；没有密钥样本与明文对照时，不要依据文件名或索引结构断定成员已加密，更不要用"能自反"代替密钥正确性验证。
